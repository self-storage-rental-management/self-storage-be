# BE-00 Shared Foundation API contract

## Conventions

- Base URL: `/api`.
- JSON fields use `camelCase`; enum values use the exact values declared by the BE enums. Reservation and payment values are `UPPER_SNAKE_CASE`; rental and return-case lifecycle values intentionally use lower-case names.
- Every protected request gets its actor, roles, session id, and facility scopes from the verified JWT. `userId`, `roles`, `facilityId`, and `facilityScope` in request bodies are ignored/rejected.
- `X-Correlation-Id` is accepted as a safe opaque value or generated by the server. The same value is returned in the response header and response body.
- Mutating requests that can be retried accept `Idempotency-Key`; the key is persisted server-side and is scoped to the authenticated actor.

## Success envelopes

Single-resource response:

```json
{
  "data": {},
  "correlationId": "uuid-or-safe-request-id"
}
```

List response:

```json
{
  "data": [],
  "pagination": {
    "page": 0,
    "pageSize": 20,
    "totalItems": 0,
    "totalPages": 0,
    "sort": "createdAt,desc"
  },
  "correlationId": "uuid-or-safe-request-id"
}
```

List APIs use zero-based `page`, a maximum `pageSize` of `100`, and support resource-specific filters such as `status`, `facilityId`, `city`, and `q`.

## Error envelope

Every API error, including Spring Security errors, uses this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": {},
    "correlationId": "uuid-or-safe-request-id"
  }
}
```

| HTTP | code | Meaning |
|---:|---|---|
| 400 | `VALIDATION_ERROR` | Malformed or invalid request data |
| 401 | `UNAUTHORIZED` | Missing, invalid, expired, or revoked authentication |
| 403 | `FORBIDDEN` | Authenticated actor lacks role or facility scope |
| 404 | `NOT_FOUND` | Resource does not exist or is outside the actor's scope |
| 409 | `CONFLICT` | Duplicate, stale, or idempotency conflict |

Internal exception details are never returned.

## Authentication

### `POST /api/auth/register`

Public. Creates a `CUSTOMER` with `PENDING_VERIFICATION` status and sends an email OTP/link. The request cannot choose role, status, or facility scope.

```json
{
  "email": "customer@example.com",
  "password": "at-least-12-characters",
  "fullName": "Nguyen Van A",
  "phone": "0900000000"
}
```

### `POST /api/auth/login`

Public. Requires an `ACTIVE` account, creates a database session, and returns a signed short-lived JWT plus a rotating refresh token containing `sub`, `sid`, `roles`, `permissions`, `facilityIds`, and `facilityScopes`.

```json
{
  "email": "customer@example.com",
  "password": "at-least-12-characters"
}
```

### `POST /api/auth/logout`

Protected. Revokes the current `sid`; the JWT is rejected afterwards even if its signature and expiry are valid.

### `GET /api/auth/me`

Protected. Returns the actor projection without password or token fields.

### Verification and password recovery

- `POST /api/auth/verify-email` verifies a one-time OTP or link token.
- `POST /api/auth/refresh` rotates a refresh token and returns a new access JWT.
- `POST /api/auth/forgot-password` creates a one-time password-reset OTP/link without exposing whether an account exists.
- `POST /api/auth/reset-password` consumes the OTP/link, updates the password, and revokes existing sessions.

## Foundation list APIs

### `GET /api/facilities`

Protected. Filters: `page`, `pageSize`, `status`, `city`, `q`. Staff and managers see only facilities present in their JWT facility scope.

### `GET /api/storage-units`

Protected. Filters: `page`, `pageSize`, `facilityId`, `status`, `unitTypeId`. Staff and managers must have the requested facility scope.

## Payment contract

### `POST /api/customer/reservations/{reservationId}/simulated-payment`

Protected. Requires `Idempotency-Key`. The server derives `initiatedBy` from JWT, takes the amount from the reservation pricing snapshot and never accepts amount or outcome from the body.

Không có request body.

Retries with the same key and the same actor return the original result. Reusing a key for a different request conflicts. The response outcome is `SUCCESS`, `FAILED` or `NOT_RECEIVED`; there is no external gateway, redirect, IPN or webhook endpoint.

## Return role contract

- `CUSTOMER` uses `/api/customer/...` for ownership-bound return requests and settlement decisions.
- `STAFF` uses `/api/staff/returns/...` for inspection, cash collection, and operational return completion.
- `MANAGER` uses `/api/manager/returns/...` for dispute review only. `rentals:update` belongs to Manager; Manager cannot execute refunds.
- `BUSINESS` uses `/api/business/returns/...` to read scoped return cases and execute an already approved refund. Business does not inspect returns, resolve disputes, or collect settlement payments; the actor must have the facility `MANAGE` scope.
- Empty facility scope never means global access. Only `ADMIN` is global; scoped roles receive an empty result or `403`/`404` according to the endpoint contract.

## File contract

### `POST /api/files`

Protected multipart upload with fields `file`, optional `entityType`, and optional `entityId`. The server accepts only JPEG, PNG, WEBP, and PDF content up to `10 MB`, verifies magic bytes, stores the file under a generated key, and returns metadata plus a SHA-256 checksum. Client filenames and paths are never used as storage paths.

## Status contract

The canonical names are declared in `com.storagehub.domain.model` and are shared verbatim by FE API services. Reservation and payment statuses are uppercase; rental and return-case lifecycle statuses are lowercase. Local demo/store models are not transport DTOs and must not be used for API requests.

Important reservation transition:

`AWAITING_PAYMENT -> CONFIRMED -> UNIT_RESERVED -> READY_FOR_CHECKIN -> AWAITING_CUSTOMER_RECEIPT -> COMPLETED`

`CONFIRMED` xác nhận reservation sau khi cọc hợp lệ, chưa phải rental đang hoạt động. `READY_FOR_CHECKIN` yêu cầu đã có gian kho cụ thể, hợp đồng và các khoản thanh toán cần thiết; sau đó Staff mới có thể check-in và kích hoạt rental.

## Mutation audit contract

Important mutations write `ActivityLog` with `actorId` (nullable for scheduled system work), `occurredAt`, `entityType`, `entityId`, `facilityId`, `beforeState`, `afterState`, and `correlationId`. Authentication events additionally write `LoginHistory`.
